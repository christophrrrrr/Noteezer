# Architecture Decision Record

## [1]. Backend language and framework

Date: 2026-09-25
Status: Superseded by [6]
Context: The app is one process with phone pages, SQLite, and two domains that Assignment 2 will split into services. The framework should be the one you would pick for that service, not a larger platform and not a second UI toolchain.
Decision: Python with FastAPI and Jinja templates, served as one process, with the standard-library `sqlite3` module behind repository functions. Inbox and reminder rules live in plain modules that do not import FastAPI. Routes validate input and call those modules.
Alternatives considered: Django was rejected because its admin, ORM, and auth stack are more than register/login and two domains need. Flask was rejected because the known next step is to split two HTTP services, and Flask does not give typed request boundaries for that split. A React frontend was rejected because one text box does not need a second toolchain. SQLAlchemy was rejected because the schema is a few tables and the tested logic should stay in our functions, not in an ORM.
Consequences: Dependencies stay at FastAPI, Uvicorn, Jinja2, and the test tools. Passwords are hashed with the standard-library `hashlib`, and the session is a signed cookie implemented in our code. Assignment 2 can move each domain module behind its own FastAPI app without rewriting the rules.

Updated: 2026-09-30. Three runtime packages were added for AI sorting: `google-genai` for Gemini, `httpx` to read link titles, and `python-dotenv` so `python app.py` can read an optional `.env` file. Gemini's free tier was chosen over Claude, which costs money per note. Ollama was rejected because it would run on a laptop without a GPU, so reading screenshots would be slow and the laptop would have to stay on. Jev was rejected because it only reads text and cannot propose folders. The cost is that Google may use free-tier notes to improve its models. The app still starts and sorts with the rules when no `GEMINI_API_KEY` is set.

Updated: 2026-10-01. `tzdata` was added because Windows has no timezone database of its own, and the app now reads times in each user's timezone with `zoneinfo`.

Updated: 2026-10-01. Lines with an image go to `gemini-3.8-flash` instead of `gemini-3.5-flash-lite`. In testing, Flash-Lite missed the date on a poster in one of two tries and Flash read it in three of three. Text lines stay on Flash-Lite, which is faster and has more free quota.

## [2]. Inbox and reminders are separate domains

Date: 2026-09-25
Status: Decided
Context: The product is one text box that becomes a note, task, link, or reminder. If the due time lived on the same row as the text, the app would be a single notes table and would be too thin for two feature domains.
Decision: Inbox owns the text, kind, tags, search, edit, delete, and task completion. Reminders own `remind_at` and status (scheduled, due, snoozed, done) in their own table, keyed by item id. The only coupling is `schedule(item_id, when)` after inbox saves an item that has a picked time. Deleting an item also removes its reminder through that same boundary.
Alternatives considered: One `notes` table with an optional `remind_at` column was rejected because reminders would not have their own responsibility or data. Making tags the second domain was rejected because the behaviour the user needs next is due, snooze, and done, which is a schedule, not a label.
Consequences: Assignment 2 can run reminders as its own service that stores item ids and due times, while inbox keeps the text. Lock-screen delivery can sit on the reminder side later without changing how lines are captured.

Updated: 2026-09-29. Folders are a third area in `noteezer/folders.py` that owns the folder tree: create, rename, move, delete, and the rule that a folder cannot move inside itself. Inbox stores which folder an item is in, but the only call it makes into folders is `require_folder(user_id, folder_id)` before it saves or moves an item. This is where automatic sorting will live, so it can later become its own service next to reminders.

Updated: 2026-09-30. Sorting lives in `noteezer/sorting.py` with its own `sort_results` table. Inbox does not call sorting at all: a line waits to be sorted when it is in Unsorted and has no sort result yet. Sorting reads those lines and files them only through `file_unsorted_item`, which does nothing if the user already moved the line. The engine sits behind a `Sorter` interface picked by the `SORTER` variable, so a Gemini engine can be added without touching inbox. A background task inside the same process runs the sorting, which the single-process rule allows. A message queue was rejected because it needs a second process.

Updated: 2026-10-01. Sorting can now change more than the folder, but only through guarded inbox functions that do nothing if the item changed meanwhile. `change_plain_note_kind` only turns a plain note into an idea or a task. `schedule_unset_reminder` only times a reminder that has no time yet. `split_item` creates the parts and hides the original. Inbox is still the only code that calls `schedule` in reminders.

Updated: 2026-10-03. The route that marks a line done read the `items` table itself, which crossed the seam. It now asks inbox with `item_kind` and `toggle_task`, and calls `complete` in reminders for a reminder. No route runs SQL anymore, so each table is read only by the module that owns it.

Updated: 2026-10-03. Which folders a line is in is still written only by inbox (`set_folders`, `add_to_folder`, `file_unsorted_item`). Sorting owns `folder_suggestions` and `folder_checks`: when a folder is created, the worker runs `check_new_folders` and stores suggestions, and `accept_also` asks inbox to add the line.

Updated: 2026-10-04. The 2026-10-03 note above went too far: no route runs SQL, but not every table is read only by its owner. Writes across a seam go through functions, with one exception: `record_reading` in `images.py` replaces the body "Screenshot" in `items` itself. Reads still cross with SQL joins: `sort_pending` and `check_new_folders` read `items`, `item_folders`, `reminders`, and `images` to find work, and `reminders`, `images`, and `links` join `items` to check the owner. These joins are what Assignment 2 has to replace, with calls between services or a `user_id` copied onto each owned table. `docs/diagrams.md` marks each crossing.

## [3]. How inbox rows relate to reminder rows

Date: 2026-09-26
Status: Superseded by [7]
Context: The two domains need a schema that matches the split. A due time on `items` would collapse them. Tags and accounts also need a place that does not become a third domain.
Decision: `items` stores body and kind for one user. `reminders` uses `item_id` as its primary key, so an item has at most one schedule, and the schedule does not copy the text. A reminder row is only created when `kind` is `reminder`. Tags are one row per user and name in `tags`, linked through `item_tags`. Accounts are `users.email` plus a password hash.
Alternatives considered: An optional `remind_at` column on `items` was rejected because inbox would own the schedule. Allowing any kind to have a due time was rejected so a task stays a task, and only a reminder item gets a schedule. Storing tags as text on the item was rejected because the same `#groceries` tag must be one record the user can filter on.
Consequences: Deleting an item deletes its reminder and tag links. The database diagram is `users` to `items` and `tags`, `items` to `item_tags` to `tags`, and `items` to `reminders` one-to-one. `schedule(item_id, when)` is the only write from inbox into reminders.

Updated: 2026-09-28. A daily reminder stores `repeat_daily` and an optional `repeat_until` on the same reminder row. `remind_at` is the next occurrence, not a copy of the text. Marking it done moves `remind_at` forward one day until that end date, or until it is turned off when no end date is set.

Updated: 2026-09-29. `folders` has `parent_id` pointing at another folder, so folders nest like Notion pages. A unique index on user, parent, and name (ignoring case) stops two sibling folders with the same name. The same name in different parents is allowed. `items.folder_id` is optional, and no folder means Unsorted. Deleting a folder deletes its subfolders (`ON DELETE CASCADE`), but items are never deleted with a folder: `ON DELETE SET NULL` moves them to Unsorted. The kind of an item (note, idea, task, link, reminder) stays separate from its folder, because a Game folder holds both tasks and ideas. Older databases are rebuilt once on startup because SQLite cannot change the kind CHECK in place. Rejected: storing a folder path as text on the item, because renaming or moving a folder would then need to rewrite every item.

Updated: 2026-09-30. `sort_results` uses `item_id` as its primary key, like `reminders`, so an item has at most one sort result, and it is deleted with the item. It stores the status (filed, review, accepted, retry, failed), the suggested `folder_id`, the confidence, the engine name, and the retry count and time. If the suggested folder is deleted, `folder_id` becomes NULL and the suggestion disappears. `proposed_name` and `proposed_parent_id` hold a new folder the engine suggests. It is only created when the user taps Create folder. `link_previews` is also keyed by `item_id` and stores the title and description of a line's first link, so a link is fetched once and not again on every retry.

Updated: 2026-10-01. `users.timezone` stores the browser's IANA zone, such as Europe/Madrid. `items.split_from` points a part at the line it was split from, with `ON DELETE SET NULL`, and `items.hidden` hides that original while its parts exist. Undo split deletes the parts and clears `hidden`. Deleting the original was rejected because a bad split could not be undone. `sort_results.suggested_remind_at` holds a time Gemini read from a line that is not a reminder, until the user accepts it. A reminder item may now exist without a `reminders` row while it waits for a time.

Updated: 2026-10-01. `images` uses `item_id` as its primary key, so a line has at most one image, and it is deleted with the line. It stores the bytes as a BLOB, the type found by `check_image`, `ai_allowed` from the checkbox, and the `title` and `text` Gemini read. Files in a folder next to the database were rejected: the assignment wants one documented SQLite path, and a folder of files could keep images whose line is gone. The cost is a larger database file; images are capped at 10 MB.

Updated: 2026-10-03. A line can now be in several folders. `items.folder_id` was replaced by `item_folders (item_id, folder_id)`, with both keys `ON DELETE CASCADE`, so deleting a folder only removes its memberships, and a line with no membership is in Unsorted. This changed because a table tennis video was filed into Table Tennis, and later it also belonged in a new Cool videos folder; with one folder per line the user had to choose. Rejected: copying the line into each folder, because an edit or a done task would then have to be kept in sync. `folder_suggestions (item_id, folder_id)` holds "Also add to" suggestions from a new-folder check, and `folder_checks (folder_id)` queues those checks. Old databases are rebuilt once on startup, and every old `folder_id` becomes a row in `item_folders`.

Updated: 2026-10-04. The diagram described in Consequences only covers the first four tables. The full database diagram, with all twelve tables from `schema.sql` and the module that writes each one, is in `docs/diagrams.md`.

## [4]. Testing approach

Date: 2026-09-30
Status: Superseded by [9]
Context: Grading needs at least 70% coverage of the core rules. The rules that could lose or misfile a note are the sorting decisions, the folder tree rules, and reminder status changes. The pages are thin code around those rules.
Decision: pytest calls the domain modules (`classify`, `inbox`, `folders`, `sorting`, `reminders`, `users`, `passwords`) directly against a real SQLite file in a temporary folder. Each test passes a fixed `now` and uses fake sorter engines. Coverage is measured on those modules only, with pytest-cov. A few `TestClient` tests check that the routes are wired up.
Alternatives considered: Mocking `sqlite3` was rejected because cascades, unique indexes, and the upgrade of old databases are rules that live in SQLite, and only a real database proves them. Browser tests were rejected because they are slow and check layout, not decisions.
Consequences: 54 tests cover 96% of those modules. The background worker loop, the routes, and the templates are tested less: a broken route shows up in the `TestClient` tests or by hand, not in the coverage number. An engine that calls an outside API will be tested with a fake, so the tests never need a network connection or a key.

Updated: 2026-10-03. The suite is now 94 tests at 96% of the domain modules, which now also include `links`, `gemini`, and `images`. Gemini, web pages, and the clock are always faked, so the tests never need a key, a network connection, or a particular day.

Updated: 2026-10-04. After lines could be in several folders, the suite is 103 tests at 96% of the same ten modules. `test_multi_folders.py` checks that deleting one folder keeps the line in its other folders and that a new folder only suggests filed lines, never moves them. `test_db.py` checks that an old database's `folder_id` values become rows in `item_folders`.

## [5]. Reminders are not pushed to the phone

Date: 2026-10-03
Status: Decided
Context: A reminder helps most when it reaches the phone at the right time, even while the app is closed. Noteezer now installs as a phone app, so push notifications look like the obvious next step.
Decision: Push notifications are not built in this assignment. A due reminder is shown at the top when the app is opened, and the background task only sorts lines; it never sends anything to the phone.
Alternatives considered: Web Push sent from the existing in-process background task fits the single-process rule, because it only calls the browser's push service. It was rejected for now because a reminder would only arrive while the computer running Noteezer is on, which is not true for a laptop at home. It also needs signing keys kept in environment variables, a table of phone subscriptions, and another dependency for encrypting the messages. A second always-on process just for notifications was rejected because the assignment allows only one.
Consequences: A reminder is missed if the app is not opened around its time. Push can be added in Assignment 2, once the app runs on an always-on server: the reminders side would store subscriptions and send due reminders, without changing how lines are captured.

## [6]. The split: inbox and reminders as two services

Date: 2026-11-12
Status: Decided
Context: Assignment 2 allows exactly two service containers, one per feature domain, each with its own database, and a static UI on an Azure Storage static website that calls both from the browser. ADR-2 named inbox and reminders as the two domains. Since then the monolith grew folders, sorting with Gemini, images, link previews, and accounts. Every table now has to belong to one service, every SQL join across the seam has to become an HTTP call or a copied column, and the browser talks to three addresses instead of one.
Decision: The seam stays where ADR-2 put it. Inbox owns accounts, lines, tags, folders, sorting, images, and link previews (`users`, `items`, `tags`, `item_tags`, `folders`, `item_folders`, `folder_suggestions`, `folder_checks`, `sort_results`, `images`, `link_previews`), and the sort worker runs inside its process. Reminders owns `reminders` and nothing else, and each row keeps a copy of the owner's `user_id`, so reminders checks ownership without asking inbox. The flow that crosses the seam lives on the server: inbox calls reminders over HTTP through one module, `reminders_client.py`, with a 2 second timeout (`REMINDERS_TIMEOUT`). It sends `PUT /reminders/{id}` when a line gets a time, from the form or from Gemini, `DELETE /reminders/{id}` when a line is deleted or stops being a reminder, and one `GET /reminders?item_id=...` per page to merge the times into the list and pin due lines on top. Inbox commits the line before it calls reminders. Done and snooze are the only client-side crossing: the UI calls reminders directly. When reminders does not answer in time, answers 5xx, or refuses the token, the client raises `RemindersUnavailable`, and inbox degrades instead of failing: the line is saved as a reminder with "no time yet" (inbox's own flag `items.needs_time`), the list shows the lines with a "Reminders are unavailable right now" banner, snooze and done show an error, and the sorter tries a time it could not store again later. Inbox owns accounts and signs every token, `v1.user.expiry.scope.signature` with HMAC-SHA256 and the shared `SESSION_SECRET` (`tokens.py`). Login gives the UI a `user` token for 90 days. Inbox makes a fresh 60-second `inbox` token for each call it makes. Only the `inbox` scope may create or delete a reminder. Every request is logged with an id that travels from inbox to reminders in `X-Request-ID`, and each service accepts browser calls only from `CORS_ORIGINS`. The UI is plain HTML, CSS, and JavaScript in `ui/`, with no build step. Inbox is a JSON API under `/api`, and the Jinja pages are gone. The UI keeps the token in `localStorage` and sends it as a bearer header to both services, and learns their addresses from a `config.js` written at deploy time (`scripts/build_ui.py`, or nginx locally). Its Content-Security-Policy allows scripts only from its own origin and calls only to the two services, and note text reaches the page only through `textContent`. `db.py`, `migrate.py`, `tokens.py`, and `middleware.py` are copied into both services, so each image stands alone, and a test fails if the copies differ.
Alternatives considered: Moving the seam to notes (items, folders, reminders) and sorting (sort results, Gemini, images, links) was rejected. Sorting reads pending lines and writes through five guarded inbox functions, so almost every sorting step would become an HTTP call, which is the sign of a seam in the wrong place. Accounts as a service of their own, and a gateway or nginx in front of both services, were rejected because the brief allows two containers. On Azure the UI and the services are on different hosts anyway, so the browser has to meet CORS either way. Putting the whole crossing in the UI was rejected: inbox needs the times itself, for the due-first order and for times Gemini reads out of a line. A message queue between the services was rejected as a third moving part for a few calls per page (and out of scope in the brief). Copying `remind_at` and `status` onto `items` was rejected, because two copies of a time drift apart and "due" changes with the clock inside reminders. Retrying a failed call inside the request was rejected, because a page would then wait several timeouts instead of one. Letting the person's own token create reminders was rejected, because reminders cannot see `items`, so anyone could claim another person's item id. A JWT library was rejected: the token needs a user id, an expiry, and a scope, and HMAC from the standard library signs that in about 30 lines that can be read in full. React with Vite was rejected, for the same reason as frameworks in ADR-1. An HttpOnly cookie was rejected because, across three addresses, it needs `SameSite=None`, credentialed CORS, and CSRF tokens, and reminders still could not read it.
Consequences: ADR-1 is superseded only for the pages, which are now a static UI instead of Jinja templates; Python, FastAPI, and the plain domain modules still hold. ADR-2 held. Every join that crossed the seam was between `items` and `reminders`, in four places: listing, finding reminder lines that still need a time, editing a line into a reminder without a time, and storing a time Gemini read. Each became one of the calls above, or the `needs_time` flag. The two services are very uneven: inbox has almost all the code, and reminders is about 150 lines of rules. Reminders cannot check that an item exists or is a reminder, so inbox calls it only for reminder lines. ADR-7 covers the integrity this loses. A time typed while reminders is down is lost, and the person picks it again. The live test on 2026-11-20 showed exactly this (`docs/evidence/partial-failure.md`): a save then took 4.5 s, two 2-second timeouts. In compose, Docker's DNS made the same save take 4.2 s, because the httpx timeout does not cover the name lookup. If inbox is down, the page cannot load at all, while reminders keeps answering its own API. A script injected into the page could read the token, so the CSP and `textContent` rules matter. Logging out only makes the browser forget the token: it stays valid until it expires, and only a new `SESSION_SECRET` ends every session. The UI needs JavaScript, and opening the inbox costs two API calls plus one per image. The cross-seam test starts the real reminders service as a second process (ADR-9). Rewritten on 2026-11-20 as one decision, from the original entry and its notes of 2026-11-15 (the seam), 2026-11-16 (the static UI), and 2026-11-17 (renumbering to the brief's topics); the earlier wording is in the git history.

## [7]. Data and migrations

Date: 2026-11-17
Status: Decided
Context: Assignment 1 kept twelve tables in one SQLite file and created them on first boot. Assignment 2 needs one SQL Server database per service (Azure SQL serverless in production), a schema that changes in place once a database holds data, and one login per service that cannot reach the other database. The split (ADR-6) also removes the foreign key from `reminders.item_id` to `items` and its `ON DELETE CASCADE` (ADR-3), because the two tables are now in different databases.
Decision: Each service has numbered SQL files in `migrations/` (`001_init.sql`, then `002_...`) and its own small runner, `migrate.py`, which runs when the service starts. Each file runs once, inside one transaction, and is recorded in `schema_migrations`; a file that fails is rolled back and stops the start. `sp_getapplock` makes a second process wait instead of running the same file twice. Files that were applied are never edited: a correction is a new file. The runner logs every file it applies, which is the startup line that shows a migration ran. Each service reads one `DATABASE_URL` (`mssql://user:password@host:port/database`) and logs in as its own user, `inbox` or `reminders`, which has `db_ddladmin`, `db_datareader`, and `db_datawriter` in its own database and no user in the other one. Locally `db/init.sql` creates both databases and both logins, with the passwords passed in from `.env`; on Azure the two users are created once during setup. The SQL was ported by hand from SQLite: `INT IDENTITY`, `NVARCHAR`, `OUTPUT INSERTED.id`, `TOP`, and `MERGE` or `IF NOT EXISTS` instead of `INSERT OR IGNORE`. SQL Server refuses two cascade paths to one table, so the cascades on `folders.parent_id` and `items.split_from` became code in `folders.py` and `inbox.py`. Integrity across the seam is kept by code: `reminders` stores a copy of the owner's `user_id`, only the `inbox` token may create or delete a reminder, and deleting a line or changing its kind calls `DELETE /reminders/{id}`. Inbox's own `items.needs_time` flag replaces the join that found reminder lines without a time. A bad migration in production is handled forward: the service with the failing file does not start, so the post-deploy health check fails and nothing half migrated is served; the fix is a new file that repairs or reverses the change, deployed through the pipeline. If a migration that succeeded damaged data, Azure SQL's point-in-time restore brings back a copy of the database from before the deploy.
Alternatives considered: Alembic was rejected because it needs SQLAlchemy, which ADR-1 already rejected for a schema this small, and the runner is about 100 lines that can be read in full. Running migrations as a step in the CD workflow was rejected: GitHub's runners would need a firewall opening to Azure SQL and a login that can change the schema, and with at most one replica (ADR-8) migrating at startup cannot run twice at once. Down-migrations were rejected because the brief allows forward only and an untested down file is worse than none. One shared `sa` login for both services was rejected because a bug or a leaked password in one service would then reach the other's data. A foreign key across the two databases is not possible.
Consequences: ADR-3 is superseded only for the link between `items` and `reminders`; the rest of its schema still holds. Integrity is lost at the seam and is now kept by code: nothing stops a reminder row from pointing at an item that no longer exists. That happens when an item is deleted while reminders is down. The leftover row is harmless, because inbox only shows times for items that exist and are reminders, but it stays until it is cleaned up by hand. A slow migration delays the first request after a deploy, because it runs before the service answers. Each service's login can change the schema, which is more than the running code needs; a separate migration login was not worth two more secrets. Migration 002 and the import of the Assignment 1 notes are added here when they are deployed.

Updated: 2026-11-19. How the data moved, and the first migration of a table that holds data. The Assignment 1 notes (one account, 7 folders, 10 lines, 2 reminders in `data/noteezer.db`) were moved by `scripts/import_a1.py`, which reads the SQLite file and recreates them through the two services' public APIs, as the UI would: inbox stores the lines and folders, and inbox gives reminders the times over the seam. Copying the rows straight into the two databases was rejected, because it would skip the rules the code enforces (kinds, folder ownership, the copy of `user_id` in reminders) and need the Azure firewall opened to the laptop. The cost is that the original dates are not kept and the password had to be set again, because only its hash was stored. Then `reminders/migrations/002_snoozed_count.sql` added `snoozed_count` to `reminders`, which already held rows on Azure: the column is added with a default of 0 and a check that it is not negative, and a reminder that was snoozed at that moment is backfilled to 1, since older snoozes were never recorded. Every snooze now adds one, and the UI shows it as "(2x)". `docs/evidence/` holds the rows before and after, and the service's startup log showed `Applied migration 002_snoozed_count.sql`. Seed data: inbox gives a new account an Examples folder with three lines that show how a line gets its kind (`app/examples.py`). It adds nothing when the account already has that folder, so it is idempotent, and the import turns it off. Reminders has no seed data, because a reminder only exists for a line someone saved.

## [8]. Serverless hosting on Azure

Date: 2026-11-18
Status: Decided
Context: Noteezer has to run without the laptop, which ADR-5 and the README named as its biggest gap, and the brief fixes the platform: Azure for Students, with $100 of credit, five allowed regions, and a list of resources that may exist. A personal capture app is idle most of the day, so nothing should cost money while nobody uses it.
Decision: Everything is in one resource group, `rg-crintz-ieu2024`, in Germany West Central, which was on this subscription's list of allowed regions and offers both Container Apps and the SQL free offer. The UI is a Storage static website (`crintzieu2024ui`, Standard LRS), and its address, https://crintzieu2024ui.z1.web.core.windows.net, is the system's public URL and the only origin both services accept. Each service is a Container App on the Consumption plan in one environment, with external HTTPS ingress, 0.25 vCPU and 0.5 GiB, and between 0 and 1 replicas. The images come from GHCR, tagged with the commit SHA and public, so no registry password is needed. The data is on one logical server, `crintz-ieu2024-sql`, with one serverless database per service (General Purpose, Gen5, 0.5 to 1 vCore, locally redundant backups) on Azure SQL's free offer, which fixes auto-pause at 60 minutes and the size at 32 GB. Each database has a contained user for its service; the server admin is used only for that setup. The firewall allows Azure services, and the laptop's IP was opened only while the users were created. The pipeline signs in as the managed identity `crintz-ieu2024-github`, with Contributor on this resource group only, through a federated credential that GitHub can use only for runs on `main`. Cold starts are handled in three places. The services retry a database connection for about a minute while a paused database resumes (error 40613, or pymssql's 20002 and 20003 timeouts). The UI wakes both services as soon as it opens, and retries reads under a "starting up" banner for about 90 seconds; writes are not retried, because one that timed out may still have been saved. The deploy waits up to about seven minutes for `/health` to report the new commit. Migrations run at startup, which is safe because there is never more than one replica, and `sp_getapplock` (ADR-7) would hold a second one back anyway.
Alternatives considered: A minimum of one replica would remove the container's cold start, but it is billed around the clock and would use up the credit, and the database would still pause. Azure Static Web Apps was rejected because the brief names the Storage static website, and a storage account is plain files with no extra service. Azure Container Registry was rejected because its Basic tier costs money every day, and GHCR is free for public images. A Log Analytics workspace, which `az containerapp env create` adds by default, was turned off (`--logs-destination none`): it is a resource outside the brief's list and is billed per GB, and `az containerapp logs show` streams the logs without it. Entra-only authentication for the database was rejected because pymssql cannot use it, and a password per service user, kept in GitHub secrets, is what the brief asks for. CORS on the Container Apps ingress was left off, because it rejects the browser's preflight for JSON requests; the services allow the UI's origin themselves (`CORS_ORIGINS`).
Consequences: While idle, nothing runs. Container Apps bills per second of use above a monthly free grant (180,000 vCPU-seconds and 2 million requests per subscription), the free offer gives each database 100,000 vCore-seconds a month and then pauses it instead of billing, storage costs cents, and GHCR is free, so a normal month should cost close to nothing. The price is the first request after a quiet period: a container starts in a few seconds, but a paused database takes up to a minute, and meanwhile Azure may answer 503 after about 30 seconds. The UI shows that as "starting up" instead of a blank page. Reminders are only checked when someone opens the app, which is why push notifications are still not built (ADR-5). At 100 times the traffic, the free offer's vCore-seconds would run out and the databases would pause until the next month, so they would move to the paid serverless tier, or to provisioned compute once they are busy all day. The Container Apps would allow more than one replica, with migrations moved into a separate step in the pipeline so that replicas never race, and a minimum of one replica during the day. The UI would get a CDN in front of the storage account, and Gemini's free tier would have to become a paid plan or be called less often.

## [9]. Pipeline and testing

Date: 2026-11-17
Status: Decided
Context: Every push has to be tested, and a merge to `main` will be deployed with no manual step (ADR-8), so CI is the only check before real data is touched. ADR-4 tested the domain modules on SQLite and measured coverage only on them. Now the same SQL must run on SQL Server, the two services meet over HTTP, and four files describe the system and must not drift from the code: two `openapi.yaml`, `system.yaml`, and `system.schema.json`.
Decision: `.github/workflows/ci.yml` runs on every push and pull request, and the CD workflow will call it first. Four jobs gate a merge. `lint` runs ruff with the rules in `ruff.toml`. `test` runs each service's tests against a throwaway SQL Server container started in the job, with a password made up and masked in that job. It fails when coverage of the service's whole `app` is below 70% (inbox is about 97%, reminders about 91%), or when `openapi.yaml` no longer matches what FastAPI generates (`scripts/openapi.py --check`). `contracts` validates `system.yaml` against the schema and both OpenAPI files against the OpenAPI specification. Then `scripts/check_system.py` checks that every variable the code reads is listed in `system.yaml`, and that every endpoint inbox calls exists in reminders' document. `build` builds both images with the commit SHA and `provenance: false`, so a Dockerfile that breaks fails before a deploy. The cross-seam test does not use a stub: the inbox test session starts the real reminders service as a second process on a free port with its own test database. Every reminder an inbox test saves crosses real HTTP with a real `inbox` token, and `test_seam.py` points inbox at a dead port and a slow server to prove the timeout and the degraded page. The OpenAPI files are generated from the code, never written by hand, and committed.
Alternatives considered: A stub for reminders was rejected because it would agree with whatever inbox expects, which is the drift the test should catch; the real process costs about two seconds per run. Running the tests against the compose stack was rejected because it needs the images built first and hides which service failed. SQLite in CI was rejected because the dialects differ, and a query that passed on SQLite could fail on Azure. A GitHub `services:` container was rejected because its password must be known when the workflow is read, so it would have to be a stored secret or written in the file. Measuring coverage only on chosen modules, as in ADR-4, was dropped because the whole app is above 70% anyway, and a chosen list can leave out what breaks.
Consequences: ADR-4 is superseded: the tests now run on SQL Server instead of SQLite, coverage counts each service's whole app, and CI runs them. A run takes about a minute, because the jobs run side by side; the slowest is the inbox tests. CI never touches Azure SQL. Deliberately not tested in CI: the UI in a real browser (a Playwright script was run by hand on 2026-11-16 and 2026-11-17, but it needs Chrome and the whole stack), the real Gemini API (always faked, so no key is needed), Azure itself (cold starts and the database resuming are checked by the post-deploy health check and by hand), and load. `system.schema.json` was written from the brief's example because the provided file was not found; if the course's file differs, CI will show where.


Updated: 2026-11-20. The first deploy that failed, on purpose. Reminders was locked out of its database on Azure (`DENY CONNECT`), and a docs PR was merged during the outage. CD run 44714488970 passed CI, pushed the images, and updated both apps, and then failed at the health check: inbox reported the new commit at the first try, but reminders' new revision could not log in to run its migrations, so it never answered. After `GRANT CONNECT`, the failed job was re-run and passed in about two minutes. The steps and logs are in `docs/evidence/partial-failure.md`. Two lessons were turned into fixes. First, the health check counted 40 attempts, but each attempt can wait 30 s for curl, so the failure took 26.7 minutes to report instead of about seven. Both services now share one 8-minute deadline. Second, the connection retry for cold starts (ADR-8) matched "20002" anywhere in pymssql's error text, and a refused login (18456) carries that text too, so every request to the locked-out service waited about a minute. The error number is now checked first, and the test uses Azure's real error text instead of a made-up one. The made-up text is why CI had not caught it. The check does not roll back: Container Apps had already moved to the new revision. Here that was right, since the code was fine and the database permission was not. A bad image would be undone by reverting the commit, which deploys again through the same pipeline.

Updated: 2026-11-24. Security scanning was added to the pipeline. For the code itself (SAST), ruff's `S` rules, Bandit's checks built into ruff, run in the lint job, and CodeQL runs in its own workflow (`codeql.yml`) on Python, the UI's JavaScript, and the workflows, because it follows data from a request to SQL, an outgoing URL, or the page, which a check of one line cannot. The eight `S` findings in app code were false positives (SQL built only from `?` placeholders or a constant column list, and binding to all interfaces in a container), each silenced on its line with the reason. For dependencies (SCA), `pip-audit` checks each service's requirements in the test job, and Trivy scans both built images, failing only on a HIGH or CRITICAL vulnerability that has a fix, because one without a fix cannot be acted on. The first run found real advisories: Starlette 0.41.3, which FastAPI 0.115.6 pulled in, python-multipart 0.0.20, and pytest 8.3.4. They were upgraded to versions at least two weeks old, which leaves time for a bad release to be noticed. Trivy's first scan failed both images too: zlib in the Debian base had a HIGH vulnerability with a fix, so the base moved to the official image's newest build (the same Python 3.13.18, an exception to the two weeks because it only carries Debian's security fixes), and pip, which is only needed while the image is built and carries its own copies of urllib3 and msgpack, is now removed from it. Every action is pinned to a full commit SHA, and Trivy is installed as one release checked against its SHA-256, because in March 2026 the tags of `aquasecurity/trivy-action` were moved to credential-stealing code, and a pipeline that used a tag would have run it with its secrets. Dependabot alerts and security updates, and GitHub secret scanning with push protection, are repository settings, not code. Rejected: Bandit and Semgrep as separate tools, which mostly repeat ruff's rules and CodeQL; Dependabot version updates, whose pull requests would arrive in the week of the submission; and an OWASP ZAP scan of the live site after each deploy, which would wake the paused database on every deploy, mostly to report missing response headers. CodeQL's first scan of main found one real bug: the email check's pattern backtracked polynomially, so one crafted 64 KB address held a worker for 16 seconds; it now stops each part at the next dot or "@" and refuses anything longer than the column, with a test that times a crafted address. Its five other findings were false positives, a log line or reminders URL built from an item id that FastAPI has already turned into an integer, and a folder link that is always relative and URL-encoded, and were dismissed in GitHub with that reason. Two days later the gate did what it is for: a pull request that changed only AI_USAGE.md failed in the build job, because Debian had meanwhile published a fix for a HIGH vulnerability in zstd that our pinned base image did not have yet. The official image's newest build, of the same Python 3.13.18, did not have the fix yet either, so both Dockerfiles now upgrade that one package from Debian's repositories, a step that does nothing once a newer base carries it, instead of ignoring the finding or leaving every build red until the image is rebuilt.

## [10]. Reminders are still not pushed to the phone

Date: 2026-11-20
Status: Decided
Context: ADR-5 left push notifications out of Assignment 1 because a reminder would only arrive while the laptop was on, and said they could be added once Noteezer runs on an always-on server. It now runs on Azure, but ADR-8 made it scale to zero: both Container Apps have 0 to 1 replicas, and both databases pause after 60 minutes without a connection. While nobody uses the app, nothing runs. Whether a reminder is due is only worked out when someone asks: `GET /reminders` compares `remind_at` with the clock and marks the row due then. A push has to be sent at the reminder's time by something that is awake at that time, without anyone opening the app.
Decision: Push notifications are still not built. A due reminder is shown at the top of the list, with its time, when the app is opened, as before. The UI wakes both services as soon as it loads, so the list is current a few seconds after opening, or up to about a minute when the database was paused. Nothing in the deployed system runs on a timer.
Alternatives considered: Web Push sent by the reminders service from a timer inside its process was rejected, because the process is only alive while requests come in. Keeping it alive means a minimum of one replica: 0.25 vCPU for a 30-day month is 648,000 vCPU-seconds, more than three times Container Apps' monthly free grant of 180,000, so it would be billed around the clock. Its checks would also keep the reminders database from ever pausing. At 0.5 vCore that is about 1.3 million vCore-seconds a month, and the free offer's 100,000 would run out in about two and a half days, after which the database pauses until the next month. A Container Apps job on a schedule (for example every five minutes) that sends due reminders was rejected for the same database cost, and because it is a third container next to the two services the brief allows. Azure Notification Hubs or a Logic App were rejected because neither is on the brief's list of resources, and both would still need something awake to find due reminders. Letting the phone schedule the notification itself was rejected because no browser ships an API for it (Chrome's Notification Triggers trial was stopped), and a reminder snoozed or finished on the laptop would still go off on the phone.
Consequences: A reminder is missed if the app is not opened around its time, which is the same gap as in Assignment 1. The cost stays close to zero (ADR-8). The services give no reason to wake up at night, so the first open of the day pays the cold start. Building push later would touch only the reminders side and the UI: a migration 003 for a `push_subscriptions` table, VAPID keys kept as GitHub secrets like `SESSION_SECRET`, a service worker that shows the message, and one sender running on a timer. That sender only makes sense once the reminders database is busy most of the day anyway, so it is the first change at 100 times the traffic, when ADR-8 already moves the databases off the free offer.
